## Bug 修复工作流

**文件**: `workflows/PLAYBOOK-bug-fix.md`

### 完整步骤

```
步骤 1: 理解问题
├── 阅读 bug 报告/用户描述
├── 确认预期行为 vs 实际行为
├── 确认复现条件
└── 搜索相关 issue/PR 历史

步骤 2: 复现 Bug
├── 找到最小复现路径
├── 在本地验证能复现
├── 如果无法复现 → 回报用户要求更多信息
└── 记录复现步骤

步骤 3: 定位问题
├── 搜索相关代码:
│   ├── grep 关键词/错误信息
│   ├── 找到入口函数
│   └── 追踪调用链
├── 查看 git blame 确认最近修改
└── 缩小范围到具体文件和行

步骤 4: 分析根因
├── 理解代码逻辑
├── 确认是逻辑错误/边界情况/竞态条件/类型问题
├── 考虑修复方案:
│   ├── 最小化修改
│   ├── 不引入新问题
│   └── 考虑边界情况
└── 如果不确定 → 列出 2-3 个方案让用户选

步骤 5: 实施修复
├── 应用最小化修改
├── 确保不破坏其他功能
├── 相关的边界情况一起处理
└── 不做不相关的重构

步骤 6: 验证修复
├── 运行相关测试
├── 运行全量 lint:
│   npm run lint && npm run typecheck  # 或
│   ruff check . && mypy .             # 或
│   cargo clippy
├── 确认 bug 不再复现
└── 确认没有引入新问题

步骤 7: 提交 PR
├── git checkout -b fix/描述
├── git add <只改了的文件>
├── git commit -m "fix: 修复描述"
├── git push
├── 创建 PR，描述:
│   ├── 问题是什么
│   ├── 根因是什么
│   ├── 修复方案是什么
│   └── 如何验证
└── 等待 CI
```

### 使用示例

对 AI 说:
```
用户: 点击"保存"按钮后页面闪烁然后数据丢失
```

AI 会按照工作流执行:
1. 搜索保存按钮相关代码
2. 找到 `handleSave` 函数
3. 发现是异步操作完成前页面就跳转了
4. 添加 `await` 和加载状态
5. 运行 lint/typecheck
6. 创建 PR

## 功能实现工作流

**文件**: `workflows/PLAYBOOK-feature-implementation.md`

### 完整步骤

```
步骤 1: 理解需求
├── 确认功能范围
├── 确认验收标准
├── 确认技术约束
└── 如果需求模糊 → 列出假设，等用户确认

步骤 2: 探索代码库
├── 找到类似的已有功能作为参考
├── 理解相关模块的结构
├── 确认要修改哪些文件
├── 查看依赖关系
└── 记录可能受影响的地方

步骤 3: 制定计划
├── 拆分为子任务
├── 确定实现顺序
├── 评估每个子任务的复杂度
└── 标记可能的风险点

步骤 4: 实现
├── 按计划逐步实现
├── 遵循现有代码风格
├── 用已有的库和工具
├── 每完成一个子任务验证一次
└── 不要做超出需求范围的事

步骤 5: Lint 和类型检查
├── npm run lint (或等效命令)
├── npm run typecheck (或等效命令)
├── 修复所有 lint 错误
└── 修复所有类型错误

步骤 6: 测试
├── 如果项目有测试框架 → 运行测试
├── 如果有新增的可测试逻辑 → 写测试
├── 确认全部通过
└── 如果用户没要求测试 → 跳过此步

步骤 7: 创建 PR
├── 分支: feat/功能描述
├── Commit: feat: 添加xxx功能
├── PR 描述:
│   ├── 实现了什么
│   ├── 关键设计决策
│   ├── 如何测试
│   └── 截图（如果是 UI 变更）
└── 等待 CI

步骤 8: CI 修复（如需要）
├── 查看 CI 失败日志
├── 修复问题
├── 新提交 push
└── 最多 3 次，之后求助用户

步骤 9: 报告完成
├── 链接 PR
├── 简要说明实现了什么
├── 提供预览 URL（如有）
└── 标记任务完成
```

## 代码重构工作流

**文件**: `workflows/PLAYBOOK-refactoring.md`

### 完整步骤

```
步骤 1: 理解重构目标
├── 确认要重构什么
├── 确认重构原因
├── 确认重构范围
└── 确认是否有行为变更（重构 = 无行为变更）

步骤 2: 评估影响
├── 找到所有使用该代码的地方
├── 评估修改范围
├── 确认测试覆盖率
└── 如果影响范围太大 → 建议分阶段进行

步骤 3: 准备
├── 确保现有测试通过
├── 记录当前行为作为基准
└── 如果没有测试 → 先补充关键测试

步骤 4: 增量重构
├── 小步修改，每步验证
├── 每步都运行 lint + 测试
├── 不要一次性改完所有东西
├── 保持每步都可回退
└── 如果中途发现问题 → 及时上报

步骤 5: 验证
├── 运行全量测试
├── 运行 lint + typecheck
├── 对比重构前后的行为
├── 检查性能（如果相关）
└── 确认没有功能退化

步骤 6: 提交
├── 分支: refactor/描述
├── Commit: refactor: 重构描述
├── PR 描述:
│   ├── 重构了什么
│   ├── 为什么重构
│   ├── 重构前后对比
│   └── 确认无行为变更
└── 等待 CI
```

### 安全重构模式

```markdown
模式 1: 提取函数
- 找到重复的代码块
- 提取为独立函数
- 替换所有使用处
- 验证行为不变

模式 2: 重命名
- 全局搜索所有引用
- 统一替换
- 检查字符串中的引用
- 运行测试

模式 3: 移动文件/模块
- 更新所有 import 路径
- 更新配置中的引用
- 检查动态引用
- 运行构建确认

模式 4: 简化条件
- 理解所有分支
- 用 guard clause 或 early return 简化
- 验证每个分支行为不变
```

## CI 修复工作流

**文件**: `workflows/PLAYBOOK-ci-fix.md`

### 完整步骤

```
步骤 1: 获取 CI 状态
├── 查看哪些 check 失败了
├── 确认是哪个步骤失败
└── 获取失败日志

步骤 2: 获取失败日志
├── 展开失败的 job
├── 找到错误信息
├── 复制关键错误行
└── 确认是否可复现

步骤 3: 分类失败原因
├── Lint 错误 → 步骤 4a
├── 类型错误 → 步骤 4b
├── 测试失败 → 步骤 4c
├── 构建失败 → 步骤 4d
└── 依赖问题 → 步骤 4e

步骤 4a: 修复 Lint
├── 运行 lint 命令获取完整列表
├── 逐个修复
├── 大部分可以 auto-fix: npm run lint -- --fix
└── 提交修复

步骤 4b: 修复类型错误
├── 运行 typecheck 获取完整列表
├── 修复类型定义
├── 不要用 any 或 @ts-ignore 绕过
└── 提交修复

步骤 4c: 修复测试
├── 本地运行失败的测试
├── 确认是你的代码导致的
│   ├── 是 → 修复代码
│   └── 可能不是 → 检查 base branch 是否也失败
├── 如果是 flaky test → 告知用户
└── 提交修复

步骤 4d: 修复构建
├── 本地运行 build
├── 通常是 import 错误或缺少依赖
├── 修复并验证
└── 提交修复

步骤 4e: 修复依赖
├── 检查 lockfile 是否正确
├── 确认新增依赖已添加到 package.json
├── 运行 install 确认无冲突
└── 提交修复

步骤 5: 验证是否已有问题
├── 如果修了 3 次还不过:
│   ├── 检查 base branch (main) 的 CI 状态
│   ├── 如果 main 也失败 → 告知用户是已有问题
│   └── 如果只有你的分支失败 → 继续修复或求助
└── 绝不随意声称 "这是已有的 flaky test"

步骤 6: 推送并验证
├── push 修复提交
├── 等待 CI 重跑
├── 确认通过
└── 如果仍失败且原因不同 → 重复步骤 1-5
```

## 脚本使用说明

### scripts/setup-project.sh

**用途**: 自动检测项目类型并安装依赖

```bash
# 使用方法
chmod +x scripts/setup-project.sh
./scripts/setup-project.sh

# 它会自动:
# 1. 检测项目类型 (Node.js/Python/Rust/Go)
# 2. 安装对应依赖
# 3. 运行 pre-commit install（如有配置）
# 4. 尝试构建项目
```

### hooks/pre-commit

**用途**: 提交前自动检查（通过 Git hook 自动调用）

```bash
# 通过 install-hooks.sh 安装后自动运行
# 也可手动运行:
./hooks/pre-commit

# 它会检查:
# 1. 密钥检测 (AWS Key, API Key, GitHub Token 等)
# 2. 禁止提交敏感文件 (.env, *.pem, credentials.json)
# 3. 大文件检查 (>5MB 警告)
# 4. 运行 lint（如有配置）
# 5. 运行 typecheck（如有配置）
```

### scripts/verify-no-secrets.sh

**用途**: 扫描代码中是否包含明文密钥

```bash
./scripts/verify-no-secrets.sh

# 它会扫描:
# - AWS Key 格式: AKIA[A-Z0-9]{16}
# - OpenAI Key: sk-[a-zA-Z0-9]{20,}
# - GitHub Token: ghp_[a-zA-Z0-9]{36}
# - Slack Token: xoxb-/xoxp-
# - 通用高熵字符串
```

## Git Hooks 说明

### hooks/install-hooks.sh

**用途**: 一键安装 Git hooks

```bash
chmod +x hooks/install-hooks.sh
./hooks/install-hooks.sh

# 安装以下 hooks:
```

### pre-commit hook

触发时机: `git commit` 之前

检查内容:
1. 是否有敏感文件被 staged
2. 是否使用了 `git add .`（警告）
3. 运行 lint（如有配置）

如果检查失败，commit 被阻止。

### commit-msg hook

触发时机: commit message 写完后

检查内容:
1. 是否符合 conventional commits 格式
2. 如果不符合，给出建议但不阻止

### pre-push hook

触发时机: `git push` 之前

检查内容:
1. 是否在 push 到 main/master（阻止）
2. 运行测试（可选）
