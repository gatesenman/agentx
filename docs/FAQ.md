# 常见问题 (FAQ)

---

## 基础问题

### Q: 这些规则文件到底是什么？

**A:** 它们是给 AI 编程助手看的"指令手册"。就像你给新员工一份工作规范文档，AI 读到这些规则后会按照指定的方式工作——遵循代码风格、不做危险操作、按流程提交 PR 等。

### Q: 放进项目后 AI 就自动遵循了吗？

**A:** 是的。每个 IDE 都有自己的自动加载机制：
- Claude Code 自动读取 `CLAUDE.md`
- Cursor 自动读取 `.cursorrules`
- Codex 自动读取 `AGENTS.md`
- 以此类推

你不需要手动"告诉" AI 去读取，放到正确位置它就会自动加载。

### Q: 我需要全部规则都用吗？

**A:** 不需要。你可以：
1. 直接用全部规则（推荐新手）
2. 只选部分章节
3. 在全部规则基础上添加自己的项目规则

### Q: 这些规则会让 AI 变慢吗？

**A:** 几乎不会。规则文件通常只有几 KB，对 AI 的上下文窗口来说微不足道。收益远大于成本。

## 安装问题

### Q: 我用 Cursor，应该用 `.cursorrules` 还是 `.cursor/rules/` 目录？

**A:** 
- **简单项目**: 用 `.cursorrules` 单文件（简单直接）
- **复杂项目**: 用 `.cursor/rules/` 目录（可以按主题分文件，支持条件加载）
- 两者可以共存，都会被加载

### Q: 团队中有人用 Cursor 有人用 Claude Code 怎么办？

**A:** 两种方案：
1. **各放各的文件** — `.cursorrules` + `CLAUDE.md` 都放进去，各自读各自的
2. **symlink** — 维护一份 `AGENTS.md`，其他文件 symlink 指向它

### Q: Monorepo 怎么配置？

**A:** 根目录放全局规则，子包放特定规则：
```
monorepo/
├── CLAUDE.md              # 全局规则
├── packages/web/CLAUDE.md # web 包特定规则
└── packages/api/CLAUDE.md # api 包特定规则
```
Claude Code / Codex 支持按目录层级合并规则。

### Q: 这些文件要提交到 git 吗？

**A:** 
- **团队规则**: 是，提交到 git（让团队共享）
- **个人偏好**: 否，加入 .gitignore（如 `CLAUDE.local.md`）

## 规则效果问题

### Q: AI 有时候不遵循规则怎么办？

**A:** 几种可能：
1. **规则太长** — 精简规则，保留最重要的。超过 32KB 可能被截断
2. **规则矛盾** — 检查是否有互相冲突的指令
3. **模型限制** — 某些模型对指令的遵循度低于其他模型
4. **上下文被挤出** — 对话太长时规则可能被遗忘，开新会话

**建议:**
- 最重要的规则放在文件前面
- 用粗体/列表等格式让规则醒目
- 关键规则重复强调（如 "绝不 force push" 多次提及）

### Q: 如何测试规则是否生效？

**A:** 
```
你: 你的工作规则是什么？简要列出核心规则。
AI: [应该能复述出你的规则要点]
```

或者测试具体行为：
```
你: 帮我 git add . 然后 push 到 main
AI: [应该拒绝，因为规则禁止这两个操作]
```

### Q: 可以让 AI 修改自己的规则吗？

**A:** 可以。比如：
```
你: 在 CLAUDE.md 中添加一条规则：所有新函数必须有 JSDoc 注释
AI: [会编辑 CLAUDE.md 文件添加该规则]
```

这是 Codex 推荐的模式——让 AI 根据你的反馈自己更新 AGENTS.md。

## 具体规则问题

### Q: "绝不 amend 提交" 是为什么？

**A:** 
- `git commit --amend` 会修改 git 历史
- 如果已经 push 了，amend 后必须 force push
- Force push 可能覆盖别人的提交
- 用新提交修复更安全，保留完整历史

### Q: "不要 `git add .`" 是为什么？

**A:** 
- `git add .` 会把所有改动都加入暂存
- 可能意外加入 `.env`、调试文件、临时文件
- 应该明确指定要加的文件: `git add src/foo.ts`

### Q: "不要修改测试让它们通过" 是什么意思？

**A:** 
- 测试失败说明代码有问题
- 修改测试让它通过 = 掩盖问题
- 应该修复代码，让原始测试通过
- 例外：如果用户说"测试需要更新"或"需求变了"

### Q: 为什么 "默认不写注释"？

**A:** 
- 好的代码本身就是文档（好的命名 > 注释）
- 注释容易过时（代码改了注释没改）
- AI 生成的注释往往是废话（"// 设置变量"）
- 只在复杂逻辑、算法、业务规则处写注释

## 工具特定问题

### Q: Aider 的 CONVENTIONS.md 和 .aider.conf.yml 有什么区别？

**A:**
- `.aider.conf.yml` — 控制 Aider 运行时行为（用什么模型、是否自动提交等）
- `CONVENTIONS.md` — 代码约定和规则（AI 的行为指令）

两者缺一不可。

### Q: Devin 的 SKILL.md 和其他 IDE 的规则文件有什么区别？

**A:**
- 其他 IDE 的规则是一个大文件，所有规则混在一起
- Devin 的 Skills 是按功能拆分的独立模块（PR流程、调试、测试各一个）
- Devin 会根据当前任务自动选择加载哪个 Skill
- 更像"功能模块"而非"规则列表"

### Q: CodeBuddy 的 CODEBUDDY.md 和 .codebuddy/rules/ 有什么区别？

**A:**
- `CODEBUDDY.md` — 简单方式，纯 Markdown，全部内容加载
- `.codebuddy/rules/` — 结构化方式，支持 alwaysApply 条件，更灵活
- 对于简单项目用 `CODEBUDDY.md` 够了
- 复杂项目推荐 `.codebuddy/rules/`

## 安全问题

### Q: 规则文件会暴露我的项目信息吗？

**A:** 规则文件本身不包含敏感信息（密钥、密码等）。但如果你自定义规则时写入了：
- 内部 API 地址
- 数据库连接信息
- 特定的安全策略细节

那就不要提交到公开仓库。把敏感部分放在 `.local` 文件中。

### Q: AI 会把规则文件内容泄露给其他人吗？

**A:** 不会。规则文件只在你的对话上下文中可见，不会被分享给其他用户或用于训练。

## 更新和维护

### Q: 这个仓库会更新吗？

**A:** 你可以定期 `git pull` 获取更新。建议：
- 不直接修改本仓库的文件
- 复制到你的项目后在项目中修改
- 定期对比本仓库的更新，选择性合入

### Q: 如何贡献规则？

**A:** 
1. Fork 本仓库
2. 添加/修改规则
3. 提交 PR
4. 说明修改原因
