# 规则系统

规则系统是 AgentX 的核心——它定义了 AI 智能体在每个 IDE 中的行为逻辑。

---

## 规则加载机制

不同 IDE 的规则加载方式不同：

| IDE | 加载方式 | 时机 |
|-----|---------|------|
| Claude Code | 读取项目根目录 `CLAUDE.md` + `CLAUDE.local.md` | 每次会话开始时 |
| Cursor | 读取 `.cursorrules`（全局）+ `.cursor/rules/*.mdc`（上下文） | 启动时 + 匹配文件时 |
| Windsurf | 读取 `.windsurfrules`（全局）+ `.windsurf/rules/*.md` | 启动时 + 匹配文件时 |
| Copilot | 读取 `.github/copilot-instructions.md` + `AGENTS.md` | 每次对话时 |
| Codex | 读取 `AGENTS.md` | 每次会话时 |
| Cline | 读取 `.clinerules/*.md`（所有文件） | 每次对话时 |
| CodeBuddy | 读取 `CODEBUDDY.md` + `.codebuddy/rules/*.mdc` | 启动时 + 匹配文件时 |
| Augment | 读取 `.augment/rules/*.md` | 按 `rule_type` 决定加载时机 |
| Aider | 读取 `.aider.conf.yml`（配置）+ `CONVENTIONS.md`（规范） | 启动时 |
| Roo Code | 读取 `.roorules`（全局）+ `.roo/rules/*.md` | 启动时 + 上下文匹配 |
| Amazon Q | 读取 `.amazonq/rules/*.md` | 对话时 |
| Qodo | 读取 `AGENTS.md` + `.qodo/agents/*.toml` | 启动时 |
| Devin | 读取 `.devin/skills/*/SKILL.md` | 按需激活 |

## 规则格式标准

### 1. 纯 Markdown 格式（Claude Code / Copilot / Codex / Cline / Amazon Q）

直接写 Markdown，无需 frontmatter：

```markdown
# 核心工作规则

## 代码质量
- 优先最小化修改范围
- 遵循现有代码风格
...
```

### 2. MDC 格式（Cursor / CodeBuddy）

需要 YAML frontmatter 头部：

```markdown
---
description: 代码质量和编辑规则。在编写或修改代码时始终应用。
globs:
alwaysApply: true
---

# 代码质量规则

## 编辑原则
...
```

**字段说明：**

| 字段 | 必填 | 说明 |
|------|------|------|
| `description` | 是 | 规则描述，IDE 用于判断是否注入 |
| `globs` | 否 | 文件匹配模式（如 `"**/*.py"`），为空表示全局 |
| `alwaysApply` | 否 | `true` 表示始终注入（Cursor 特有） |

### 3. Augment 规则格式

需要 YAML frontmatter 指定 `rule_type`：

```markdown
---
rule_type: always_apply
---

# 核心规则
...
```

**`rule_type` 选项：**

| 值 | 说明 |
|----|------|
| `always_apply` | 每次对话都注入 |
| `agent_requested` | AI 自行判断是否需要 |
| `manual` | 仅用户手动引用时加载 |

### 4. YAML 配置格式（Aider）

```yaml
# .aider.conf.yml
model: claude-3-5-sonnet-20241022
edit-format: diff
auto-lint: true
map-tokens: 4096
map-refresh: auto
read:
  - CONVENTIONS.md
aiderignore: .aiderignore
```

### 5. TOML 配置格式（Qodo）

```toml
# .qodo/agents/code-agent.toml
[agent]
name = "code-agent"
description = "代码智能体 — 编码、审查、调试"

[agent.instructions]
general = """
你是高级软件工程师...
"""
```

### 6. Devin Skill 格式

```markdown
---
name: pr-workflow
description: PR 创建工作流。当需要创建 Pull Request 时使用。
---

# PR 工作流

## 步骤
1. 确认所有修改已完成
...
```

**必填字段：**

| 字段 | 说明 |
|------|------|
| `name` | 技能唯一标识（小写、用连字符） |
| `description` | 技能描述（Devin 用于判断是否激活） |

## 规则优先级

当多个规则冲突时的优先级（从高到低）：

1. **用户实时指令** — 用户在对话中给出的指令最高
2. **本地规则** — `CLAUDE.local.md` 等本地覆盖文件
3. **项目规则** — `CLAUDE.md`、`.cursorrules` 等
4. **上下文规则** — `.cursor/rules/*.mdc` 中按 `globs` 匹配的
5. **全局规则** — IDE 全局设置中的规则
6. **默认行为** — IDE 内置的默认行为

## 自定义规则

### 添加新规则

以 Cursor 为例，添加一个 Python 专用规则：

```bash
# 创建新规则文件
cat > .cursor/rules/python-rules.mdc << 'EOF'
---
description: Python 代码规则。编写或修改 Python 文件时自动应用。
globs: "**/*.py"
alwaysApply: false
---

# Python 编码规范

## 类型注解
- 所有函数参数和返回值必须有类型注解
- 使用 `from __future__ import annotations` 延迟求值

## 导入规范
- 标准库 → 第三方库 → 项目内部（空行分隔）
- 使用 `isort` 排序

## 测试
- 使用 `pytest` 框架
- 测试文件命名: `test_<module>.py`
- 使用 `pytest.fixture` 管理 fixtures
EOF
```

### 修改现有规则

直接编辑对应的规则文件即可。建议：
- 保留现有结构和标题
- 增加内容而非删除
- 修改后在 IDE 中验证加载是否正常

### 禁用某条规则

- 直接从规则文件中删除对应段落
- 或在段落前加 HTML 注释 `<!-- ... -->`

## 规则编写最佳实践

1. **具体优于模糊** — "使用 4 空格缩进" 优于 "保持一致的缩进"
2. **命令式语气** — "使用 const，不用 let" 而非 "建议使用 const"
3. **给出示例** — 每条规则配一个正面和反面示例
4. **控制长度** — 单个规则文件不超过 500 行，超了就拆分
5. **定期更新** — 随项目演进更新规则，删除过时内容
