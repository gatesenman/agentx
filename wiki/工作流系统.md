# 工作流系统

AgentX 提供 4 个标准化 Playbook 工作流，覆盖日常开发中最常见的任务类型。

---

## 工作流总览

| 工作流 | 文件 | 适用场景 |
|--------|------|---------|
| Bug 修复 | `workflows/PLAYBOOK-bug-fix.md` | 定位和修复代码缺陷 |
| 功能实现 | `workflows/PLAYBOOK-feature-implementation.md` | 从零开始实现新功能 |
| 代码重构 | `workflows/PLAYBOOK-refactoring.md` | 优化现有代码结构 |
| CI 修复 | `workflows/PLAYBOOK-ci-fix.md` | 修复持续集成构建/测试失败 |

---

## Bug 修复工作流

### 完整流程

```
用户报告 Bug
    │
    ▼
[1] 复现问题
    ├─ 阅读 Bug 描述、错误日志
    ├─ 搜索相关代码: grep + find_file_by_name
    ├─ 理解代码逻辑: read 相关文件
    └─ 在本地复现（运行测试或手动触发）
    │
    ▼
[2] 定位根因
    ├─ 分析调用链: grep 函数引用
    ├─ 检查 git blame: 找到引入 Bug 的提交
    ├─ 添加 console.log / print 调试（如需要）
    └─ 确认根因，记录发现
    │
    ▼
[3] 制定修复方案
    ├─ 最小化修改范围
    ├─ 评估影响面：可能影响哪些功能
    └─ 检查是否有相关测试需要更新
    │
    ▼
[4] 实现修复
    ├─ 创建分支: git checkout -b devin/$(date +%s)-fix-xxx
    ├─ 编辑代码: edit / MultiEdit
    ├─ 运行 lint + typecheck
    └─ 运行相关测试
    │
    ▼
[5] 提交和 PR
    ├─ git add <具体文件>
    ├─ git commit -m "fix: 修复 xxx 问题"
    ├─ git push
    ├─ 创建 PR（fetch_pr_template → git_create_pr）
    └─ 等待 CI 通过
```

### 决策分支

| 情况 | 处理 |
|------|------|
| Bug 无法本地复现 | 检查环境差异、添加更详细的日志、请求用户提供更多信息 |
| 修复影响面大 | 拆分成多个小 PR，分步提交 |
| 根因在第三方依赖 | 检查是否有新版本修复，或寻找 workaround |
| 有多个可能的根因 | 逐个排除，添加诊断日志 |

## 功能实现工作流

### 完整流程

```
功能需求
    │
    ▼
[1] 需求分析
    ├─ 理解用户需求
    ├─ 搜索现有代码：是否有类似实现可参考
    ├─ 确定涉及的模块和文件
    └─ 创建 TODO 列表
    │
    ▼
[2] 技术设计
    ├─ 确定 API 接口 / 组件结构
    ├─ 选择实现方案（优先复用现有模式）
    ├─ 识别需要修改的文件清单
    └─ 评估是否需要新增依赖
    │
    ▼
[3] 分步实现
    ├─ 创建分支: git checkout -b devin/$(date +%s)-feat-xxx
    ├─ 按 TODO 列表逐步实现
    ├─ 每完成一个子任务就标记完成
    ├─ 遵循现有代码风格和模式
    └─ 不引入不必要的依赖
    │
    ▼
[4] 质量验证
    ├─ 运行 lint（eslint / ruff / clippy 等）
    ├─ 运行 typecheck（tsc / pyright / mypy 等）
    ├─ 运行现有测试（确保没有回归）
    └─ 如果有测试要求，编写新测试
    │
    ▼
[5] 提交和 PR
    ├─ 按逻辑分组提交（不要一个大 commit）
    ├─ 每个 commit message 遵循 Conventional Commits
    ├─ 创建 PR，描述按模板填写
    └─ 等待 CI 通过
```

### 关键原则

- **优先复用** — 检查项目中是否有类似的实现可以参考或复用
- **增量实现** — 先实现核心功能，再迭代完善
- **最小依赖** — 不引入项目未使用的新库，除非确实必要
- **保持一致** — 新代码风格必须与现有代码一致

## 代码重构工作流

### 完整流程

```
重构需求
    │
    ▼
[1] 评估现状
    ├─ 阅读待重构的代码
    ├─ 理解原有逻辑和意图
    ├─ 搜索所有调用方（grep 函数名 / 类名）
    └─ 确认测试覆盖率
    │
    ▼
[2] 制定计划
    ├─ 确定重构目标（可读性 / 性能 / 可维护性）
    ├─ 列出所有需要修改的文件
    ├─ 评估风险：是否会破坏现有功能
    └─ 确定验证方法
    │
    ▼
[3] 分步重构
    ├─ 一次只改一件事
    ├─ 每步都确保测试通过
    ├─ 使用 IDE 重命名功能（如有）而非手动替换
    └─ 保持 git 历史清晰
    │
    ▼
[4] 验证
    ├─ 运行完整测试套件
    ├─ 运行 lint + typecheck
    ├─ 对比重构前后的行为是否一致
    └─ 检查是否有遗漏的引用
    │
    ▼
[5] 提交
    ├─ commit message 使用 refactor: 前缀
    └─ PR 描述说明重构动机和方法
```

### 重构类型决策树

```
重构需求 → 什么类型？
    │
    ├─ 命名优化 → 使用全局替换（grep + edit replace_all）
    ├─ 函数拆分 → 提取函数，更新调用方
    ├─ 模块重组 → 移动文件，更新导入
    ├─ 类型增强 → 添加类型注解，修复类型错误
    └─ 性能优化 → 基准测试 → 修改 → 再次基准测试
```

## CI 修复工作流

### 完整流程

```
CI 失败通知
    │
    ▼
[1] 获取失败信息
    ├─ git_pr_checks: 查看哪些 check 失败
    ├─ git_ci_job_logs: 获取失败 job 的详细日志
    └─ 分类失败类型
    │
    ▼
[2] 分类诊断
    ├─ 编译错误 → 检查类型错误、缺失导入
    ├─ Lint 错误 → 运行 lint 修复
    ├─ 测试失败 → 读取失败的测试、理解断言
    ├─ 构建超时 → 检查依赖安装、缓存配置
    └─ 环境问题 → 检查 CI 配置、依赖版本
    │
    ▼
[3] 验证是否为预存问题
    ├─ 检查 base 分支 CI 状态
    ├─ 如果 base 也失败 → 通知用户（预存问题）
    └─ 如果仅本分支失败 → 修复
    │
    ▼
[4] 修复
    ├─ 本地复现失败
    ├─ 应用修复
    ├─ 本地验证通过
    └─ 推送并等待 CI
    │
    ▼
[5] 结果验证
    ├─ git_pr_checks 等待所有 check 通过
    ├─ 如果仍然失败 → 重复步骤 2-4（最多 3 次）
    └─ 3 次后仍失败 → 上报用户
```

### CI 失败类型速查

| 失败类型 | 常见原因 | 修复方法 |
|---------|---------|---------|
| TypeScript 编译失败 | 类型不匹配、缺失导入 | 运行 `tsc --noEmit`，逐个修复 |
| ESLint 错误 | 格式/风格问题 | `npx eslint --fix` |
| Python 类型检查 | mypy/pyright 报错 | 修复类型注解 |
| 单元测试失败 | 断言不匹配 | 阅读测试，修改实现（不修改测试） |
| E2E 测试失败 | UI 变更导致 | 检查选择器、等待时间 |
| 构建失败 | 依赖缺失 | 检查 package.json / requirements.txt |
| 安全扫描失败 | 依赖漏洞 | 升级依赖版本 |

## 工作流自定义

### 添加自定义工作流

在任何 IDE 的 `workflows/` 目录下创建新文件：

```markdown
# PLAYBOOK-<名称>.md

# <工作流名称>

## 触发条件
- 什么时候使用这个工作流

## 前置条件
- 需要什么工具/权限/环境

## 执行步骤
### 第一步: xxx
### 第二步: xxx
...

## 决策分支
| 情况 | 处理 |
|------|------|

## 完成标准
- 什么条件算完成
```

### 工作流选择决策树

```
收到任务
    │
    ├─ 报了 Bug？ ──────────→ Bug 修复工作流
    ├─ 要新功能？ ──────────→ 功能实现工作流
    ├─ 要优化代码？ ────────→ 代码重构工作流
    ├─ CI 挂了？ ──────────→ CI 修复工作流
    └─ 其他 → 直接按规则执行
```
