## 1. 提示词基本原则

### 1.1 结构化胜于自然语言

```
❌ "帮我修一下那个登录页面的 bug，就是那个点了没反应的"

✅ "修复 src/pages/Login.tsx 中登录按钮点击无响应的问题
   - 复现: 输入用户名密码后点击登录按钮，页面无反应
   - 预期: 应跳转到 /dashboard
   - 相关文件: src/services/auth.ts, src/hooks/useAuth.ts"
```

### 1.2 给出验证标准

```
❌ "优化这段代码"

✅ "优化 processData 函数的性能
   - 当前: 处理 10000 条记录需要 5 秒
   - 目标: 降低到 1 秒以内
   - 约束: 不改变函数签名和返回值格式
   - 验证: npm run test:perf 应该通过"
```

### 1.3 明确范围和限制

```
❌ "重构用户模块"

✅ "重构 src/modules/user/ 下的代码:
   - 把 UserService 类拆分成 UserQueryService 和 UserCommandService
   - 不改变公开 API（外部调用方不需要修改）
   - 保持现有测试通过
   - 不修改数据库 schema"
```

## 2. 10 类高效提示词模式

### 模式 1: Bug 修复模式

```
修复 [组件/文件] 中的 [问题描述]

复现步骤:
1. [步骤1]
2. [步骤2]

实际行为: [当前发生了什么]
预期行为: [应该发生什么]
相关文件: [文件路径列表]
错误信息: [如果有]
```

**示例**:
```
修复 src/components/UserList.tsx 中的无限重渲染问题

复现步骤:
1. 打开 /users 页面
2. 观察浏览器控制台

实际行为: 组件不断重渲染，控制台持续输出日志，最终页面卡死
预期行为: 组件只在数据变化时重渲染
相关文件: src/hooks/useUsers.ts, src/contexts/UserContext.tsx
错误信息: Warning: Maximum update depth exceeded
```

### 模式 2: 功能实现模式

```
实现 [功能名称]

需求:
- [需求1]
- [需求2]

技术约束:
- 使用 [技术/库]
- 遵循 [设计模式/架构]

验收标准:
- [标准1]
- [标准2]

参考: [现有类似功能的文件路径]
```

### 模式 3: 代码探索模式

```
分析 [模块/系统] 的实现:

想了解:
1. 数据流: 从 [入口] 到 [出口] 经过了哪些组件
2. 关键依赖: 这个模块依赖了什么外部服务
3. 状态管理: 状态是怎么存储和更新的
4. 错误处理: 异常情况是怎么处理的

不需要修改代码，只需要分析和解释。
```

### 模式 4: 重构模式

```
重构 [目标代码]:

目标: [重构的具体目标，比如提取公共逻辑、降低圈复杂度]
范围: 只修改 [目录/文件列表]
约束:
- 不改变公开 API
- 所有现有测试必须通过
- 不引入新依赖

采用增量提交，每步都可验证。
```

### 模式 5: 测试编写模式

```
为 [模块/函数] 编写测试:

覆盖场景:
- 正常路径: [描述]
- 边界情况: [描述]
- 错误情况: [描述]

使用框架: [Jest/Vitest/pytest/等]
Mock 策略: [需要 mock 什么]
参考现有测试: [路径]
```

### 模式 6: 迁移/升级模式

```
将 [库/框架] 从 v[X] 升级到 v[Y]

当前使用方式: [简述]
Breaking Changes 参考: [changelog/migration guide URL]
优先级: 先升级核心，再升级周边
验证: 所有测试通过 + 手动验证 [关键功能]
```

### 模式 7: 安全审查模式

```
审查 [模块] 的安全性:

关注:
1. 输入验证和 sanitization
2. 认证和授权检查
3. 敏感数据处理
4. SQL 注入/XSS 风险
5. 依赖漏洞

输出: 问题列表 + 修复建议（不直接修改代码）
```

### 模式 8: 性能优化模式

```
优化 [目标] 的性能:

当前指标: [具体数据，如响应时间、内存用量]
目标指标: [期望达到的数据]
分析工具: [profiler/benchmark 命令]
约束: 不改变功能行为
```

### 模式 9: 文档编写模式

```
为 [模块/API] 编写文档:

包含:
- 概述和用途
- API 签名和参数说明
- 使用示例（至少 2 个）
- 常见问题

格式: [JSDoc/docstring/README/等]
风格: 匹配项目现有文档风格
```

### 模式 10: CI/部署模式

```
配置 [CI工具] pipeline:

阶段:
1. Lint + Type Check
2. 单元测试
3. 集成测试
4. 构建
5. 部署到 [环境]

触发条件: [push to main / PR / tag]
密钥: 使用 CI 的 secrets 管理，不硬编码
参考: [现有 CI 配置路径]
```

## 3. 上下文构建技巧

### 3.1 提供文件路径

给智能体明确的文件路径可以大幅减少搜索时间:

```
✅ "修改 src/services/auth.ts 第 42 行的 validateToken 函数"
❌ "修改认证相关的代码"
```

### 3.2 提供错误日志

直接粘贴错误日志比描述错误更有效:

```
✅ "运行 npm test 出现以下错误:
    TypeError: Cannot read property 'id' of undefined
      at UserService.getUser (src/services/user.ts:25:15)
      at Object.<anonymous> (tests/user.test.ts:10:5)"

❌ "测试跑不通，好像是 user 那块有问题"
```

### 3.3 提供预期的输入输出

```
✅ "formatDate 函数:
    输入: '2024-01-15T10:30:00Z'
    当前输出: '2024-01-15'
    预期输出: '2024年1月15日 10:30'"

❌ "日期格式不对"
```

### 3.4 利用规则文件注入上下文

在 CLAUDE.md / .cursorrules 中添加项目特定信息:

```markdown
## 项目上下文

- 前端: Next.js 14 (App Router) + Tailwind CSS
- 后端: FastAPI + SQLAlchemy
- 数据库: PostgreSQL 15
- 部署: Vercel (前端) + Railway (后端)
- 认证: Clerk
- 测试: Vitest (前端) + pytest (后端)
```

## 4. 反模式（不要这样做）

### 4.1 过于模糊

```
❌ "帮我改改代码"
❌ "优化一下"
❌ "出错了"
```

### 4.2 过于详细的实现指令

```
❌ "在第 15 行添加 const x = 1，
    然后在第 16 行添加 if (x > 0) {，
    然后在第 17 行添加 console.log(x)，
    然后在第 18 行添加 }，
    ..."

✅ "添加一个计数器功能，当值 > 0 时输出日志"
```
→ 给目标，不给逐行指令。智能体比你更了解代码上下文。

### 4.3 同时给太多任务

```
❌ "修复登录 bug，同时重构用户模块，
    然后添加新的支付功能，
    还有把测试覆盖率提到 80%"

✅ 一次一个任务，或者明确优先级:
   "按以下顺序处理:
    1. [P0] 修复登录 bug
    2. [P1] 重构用户模块
    3. [P2] 添加支付功能"
```

### 4.4 不提供验证标准

```
❌ "改好了告诉我"

✅ "完成后确认:
    1. npm run test 全部通过
    2. npm run lint 无错误
    3. /api/users 端点返回正确的 JSON"
```

### 4.5 不信任智能体的搜索能力

```
❌ 手动描述整个代码架构给智能体

✅ "先阅读 src/modules/ 下的代码，了解现有架构后再实现"
```
→ 智能体可以自己搜索和理解代码，给方向比给细节更好。

## 5. 项目特定提示词配置

### 5.1 在规则文件中预设上下文

```markdown
# CLAUDE.md 示例

## 项目架构
- src/pages/: 页面组件 (Next.js App Router)
- src/components/: 可复用 UI 组件
- src/services/: 业务逻辑
- src/hooks/: 自定义 React hooks
- src/types/: TypeScript 类型定义

## 命名约定
- 组件: PascalCase (UserList.tsx)
- hook: camelCase, 以 use 开头 (useAuth.ts)
- 服务: camelCase (authService.ts)
- 类型: PascalCase, 以 I 开头 (IUser)
- 常量: UPPER_SNAKE_CASE

## 常用命令
- 开发: npm run dev (localhost:3000)
- 测试: npm test
- Lint: npm run lint
- 类型检查: npx tsc --noEmit
- 构建: npm run build
```

### 5.2 本地覆盖 (CLAUDE.local.md)

```markdown
## 个人偏好
- 总是用中文回复
- 提交前运行完整测试套件
- 用 Vim 快捷键风格的命名

## 开发环境
- 本地数据库: localhost:5432/myapp_dev
- 测试账号: test@example.com / $TEST_PASSWORD
- API 基础 URL: http://localhost:8000
```

## 6. 多轮对话策略

### 6.1 渐进式细化

```
第1轮: "分析 src/services/ 下的代码结构"
第2轮: "基于你的分析，重构 UserService 和 OrderService 的公共逻辑"
第3轮: "为新提取的 BaseService 添加单元测试"
```

### 6.2 确认后再执行

```
"分析这个 bug 的可能原因，给我你的分析但先不要修改代码"
→ 确认分析正确后
"你的分析正确，按方案 2 修复"
```

### 6.3 中途调整

```
"等一下，不要改 API 层的代码了。
 只修改 service 层，保持 API 层不变。
 继续之前的修复，但跳过 routes/ 目录。"
```

## 7. 复杂任务分解

### 7.1 大功能拆分策略

```
功能: 用户通知系统

拆分:
PR1: 数据模型和数据库迁移
PR2: 后端 API (创建/查询/标记已读)
PR3: 前端通知组件
PR4: WebSocket 实时推送
PR5: 邮件通知集成

每个 PR 独立可合并，不依赖后续 PR。
```

### 7.2 并行任务组织

```
可以并行的:
- 修复 bug A (影响用户模块)
- 修复 bug B (影响支付模块)
→ 两个 bug 在不同模块，不冲突

必须串行的:
- 重构数据库 schema
- 更新依赖此 schema 的 API
- 更新使用此 API 的前端
→ 每步依赖前一步，必须按序
```

### 7.3 检查点设置

```
"实现用户注册功能。每完成以下步骤暂停让我确认:

检查点1: 数据模型设计完成
检查点2: API 端点实现完成
检查点3: 前端表单完成
检查点4: 验证和错误处理完成
检查点5: 测试通过"
```

## 速查: 提示词质量自检清单

写完提示词后快速自检:

- [ ] 有明确的目标（做什么）
- [ ] 有明确的范围（改哪些文件/模块）
- [ ] 有验证标准（怎么确认做对了）
- [ ] 提供了相关文件路径或错误日志
- [ ] 指定了约束（什么不能改）
- [ ] 如果是 bug，给了复现步骤
- [ ] 一次只有一个主要任务
